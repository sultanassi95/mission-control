# epic-flow

The altitude above `/mission-flow`: that flow's contract is one ticket -> one
branch -> one PR, and it stays untouched. epic-flow plans work that is bigger
than one ticket and executes it BY composing mission-flow - so every standard
the child flow enforces is inherited per fragment, and this skill adds only
what per-ticket machinery structurally cannot see: decomposition discipline,
cross-fragment coverage, and the cross-fragment review.

Full design + rationale: the MC-017 ticket folder (`design.md` there is the
authority where this text summarizes).

## Invocation

```
/epic-flow <description | epic-key> [--front <f>] [--project <p>]
           [--tracker jira|github|native] [--decide minor]
           [--spend lean|standard|deep]
/epic-flow --execute <epic-id>
```

Default run = PLAN: E0 through the E6 tree lock, then STOP - the founder's
lock IS the execution grant. `--execute` resumes any later session from the
folder. **Execution mode (E7/E8) lands with build units B1/B2; until they
ship, `--execute` reports the locked tree and stops.** [STUB - B1/B2]

## The execution surface

Plan mode surfaces one session task per stage (`<EPIC> · E0 Face` ...
`<EPIC> · E8 Close`), transitioned at stage gates - the same contract as
mission-flow's per-phase list (MC-027). Execution mode additionally creates a
fresh per-phase list per child, per that rule.

## The epic folder

Single-project epics live under that project's `tasks/`; cross-project epics
under a front-level `tasks/` beside the hub. Epic id = the tracker's epic key,
or the native board's next id.

```
tasks/<EPIC-ID>-<slug>/
  ticket.md            epic-level ticket (external tracker: pointer + DoD checklist)
  00-face.md           E0
  10-current-state.md  E1
  20-architecture.md   E2 (carries the machine-readable "## Declared outputs")
  30-fragments/        E3 - one brief per fragment, from the kit template
  40-coverage.md       E4 - GENERATED by tools/epic-coverage.sh, never hand-edited
  50-sequence.md       E5
  60-tree-lock.md      E6 - the founder's lock
  records/             stage dispatch records (mission-flow record schema)
```

Every stage document is diagram-first (`framework/visualization-contract.md`)
and carries a `status: draft | locked | superseded | retired` header. An edit
to a `locked` document is a logged deviation, never a silent rewrite. E0
ensures the front's docs-viewer is up so the founder watches the plan take
shape live (mechanics: the E0 stage below).

Fragment briefs are the state machine - frontmatter per
`framework/kit/templates/_epic-fragment.template.md`: `id` (`<EPIC-ID>.<n>`),
`title` (becomes the squash-commit subject), `state`
(`pending|in-progress|squashed|invalidated`), `depends_on`, `ticket` (tracker
key, filled at E6), `outputs` (**owned deliverables, never merely touched
files** - kinds: schema | route | file | artifact | job), `size`, `squash`
(commit hash), `decide_log`.

## The stages

### E0 - Face (inline; gate: founder locks the face)

`00-face.md`: the outcome, explicit non-goals, and OUTCOME-LEVEL acceptance -
evidence-typed exactly like Phase-2 criteria, stated against the terminal
artifact a user consumes. The epic-level terminal assertion is declared here.
One page; correcting a face costs a paragraph, which is why it is the first
gate.

**E0 also brings the plan's window up.** The docs-viewer is root-pinned by
design, so the pattern is reuse-or-generate at the FRONT's portfolio dir
(`_command/portfolio/<front>/`), where the epic folder appears in the live
sidebar with its mermaid diagrams pre-rendered:

1. A viewer already serving that dir (its `docs-viewer-server.cjs` process is
   running)? Reuse it - report the URL, touch nothing.
2. The files exist but nothing is serving? Start it (`npm run docs-viewer`
   from that dir) and report the URL.
3. Nothing exists? Run `/docs-viewer` WITH that dir as the project root
   (generate, install its dev-dependencies there, start), then report the URL.

The server is LEFT RUNNING at every exit of every stage - the founder is
usually watching it, and tearing down a viewer mid-plan is the shared-stack
mistake in miniature. Port conflicts resolve by the viewer's own free-port
scan; the URL lands in `00-face.md`'s header line so a resumed session finds
the running window before starting a second one.

### E1 - Current-state audit (dispatched, read-only; no gate)

`10-current-state.md`: what exists, as evidence - the code and infra actually
touched (default agent: a read-only explorer), real telemetry, one resolved
data-path identifier, the blast radius from `_map.md`, and the
ALREADY-DELIVERED SCAN at epic scale (`git log origin/<base> --grep` per
surface: on a real epic, 3 of 8 planned tickets were already shipped). The
conformance reference is recorded here for every surface the epic touches -
what THIS project and this front already do (reference order: this project ->
front siblings -> declared quality profile).

### E2 - Lo-fi architecture (dispatched + inline judgment; gate: founder settles each fork)

`20-architecture.md`, diagram-first, boundary-level only:

- every component boundary justified against single-responsibility;
- every edge names its CONTRACT - interface, not internals - with dependency
  direction drawn and inversions explicit;
- **reuse-first as a gate:** the doc names what EXISTS and is reused versus
  built new, and every build-new names why reuse fails - the Phase-5
  named-counterpart evidence bar, moved to the moment it is cheapest;
- production-execution reality per moving part;
- the 13-layer touch-list: which SDLC layers the epic touches, each naming its
  hook (layer 9 -> compliance profile, layer 12 -> per-fragment telemetry
  criteria, ...);
- `## Declared outputs` - the machine-readable list E4 diffs against
  (`- <kind>: <name>` per line);
- genuine forks presented to the founder one by one, each settled fork
  recorded via `/adr`.

### E3 - Fragmentation (inline; no gate - E4/E6 gate it)

One brief per fragment, cut by SOLID: one responsibility each (SRP); fragment
boundaries are interface boundaries - consumers depend on a fragment's
declared contract (ISP); prefer fragments that EXTEND existing modules over
rewriting shared cores (OCP - also what keeps merge-backs conflict-free);
shared logic gets ONE owning fragment that others `depends_on` (DRY - enforced
mechanically at E4). Briefs are LO-FI: scope, declared outputs, evidence-typed
acceptance, a telemetry criterion for any new user-critical path. Hi-fi design
is JIT inside each child's own Phase 1, never up front.

### E4 - Coverage (script; GATE: exit 0 required)

Run `tools/epic-coverage.sh <epic-folder>`. It diffs the union of fragment
`outputs:` against E2's `## Declared outputs` and writes `40-coverage.md`.
**Exit 1 on any unclaimed remainder (a declared output no fragment owns) and
on any over-claim (one output owned twice - duplication scheduled in
advance).** A remainder gets a fragment BEFORE E5, never as a follow-up. The
gate re-runs whenever the tree changes, and again at E8 against SHIPPED
artifacts.

### E5 - Sequencing & risk (inline; no gate)

`50-sequence.md`: the dependency graph, lane order, and per-fragment spend
estimates from `/spend`'s observed history by size class - no history means
"no baseline" and only the runaway FACTOR (default x3), never an invented
absolute. **The walking skeleton is the first lane:** one thin slice through
every boundary proves production-execution reality before the bulk is built;
riskiest interface first thereafter.

### E6 - Tree lock (inline; GATE: the founder locks the tree)

Every brief meets the Phase-2 floor before the founder is asked - the lock is
informed, not hopeful. File the children in the tracker (`--parent <EPIC-ID>`
per child; child type derived from the epic), fill each brief's `ticket:`
field, write `60-tree-lock.md` (tree summary, tracker keys, date, the
founder's word). **The lock is the execution grant** for exactly this tree in
E5's order.

### E7 / E8 - Execute and close [STUB - lands with B1/B2]

The contract, so the lock is signed with eyes open (full text: the design):
one epic branch (`epic/<key>-<slug>`, MC-018 discipline, push authority to
THIS branch only - the deploy base excluded as everywhere); each child runs
full `/mission-flow` with `--parent`, `--base <epic-branch>`, and Phase 7
replaced by a squash onto the epic branch; epic-branch CI watched per squash
(MC-022); base drift merged in at lane boundaries (merge, never rebase);
serial lanes in v1; Phase 6 never amortized; children park in review at
squash and reach Done in a batch when the founder merges the epic PR. E8:
coverage re-run against shipped artifacts, the CROSS-FRAGMENT principles pass
over the whole epic diff (per-child review structurally cannot see
cross-child duplication), the E0 acceptance verified on the terminal
artifact, the epic PR (commits = review index), `/as-built`, the tally.

## Autonomy

The E6 lock grants autonomous execution of the locked tree, in order, no
re-asking between children - and nothing outside the tree, ever. Stops stay
per-child and pause the fragment + its dependents; independent lanes continue.
Under `--decide minor` the orchestrator may settle decisions that pass ALL
five rubric conditions - reversible within the epic branch AND no
schema/data-model choice AND no cross-fragment contract change AND no
product-visible behaviour fork AND no new dependency (dev included; an
authored migration is a schema choice; config only if reversible, not
product-visible, and touching no secret/infra surface). Each minor decision:
one real-time line, appended to the brief's `decide_log`, enumerated at E8,
proposed to `/adr`. This rubric IS the definition of a trivial fork for every
child under the run - one vocabulary, not two. Anything failing it stops.

**Retiring an epic** is the founder's call at any boundary: children closed
with the reason, the branch left in place, the folder's status `retired`. An
abandoned epic that looks active is worse than a retired one.
